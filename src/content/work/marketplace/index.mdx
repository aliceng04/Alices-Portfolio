## 1. The goal of this case study.

Show how I scoped a marketplace, similar to Shopee, into an MVP that can run real orders: which products it needs, how they connect, and the rules that decide what happens to an order, and to the money, at every step.

## 2. Problem statement.

<KeyInsight label="Problem statement">
In a marketplace the buyer pays a stranger. Buyers need to pay safely and get their money back when something goes wrong; sellers need to sell without building a store; the platform has to prove the loop, and its commission, works.
</KeyInsight>

So trust is the product. The MVP is not "a shopping app"; it is a promise that the money is held until both sides are happy, and that every problem has a clear owner and a clear deadline.

## 5. Business model.

Shopay earns a commission on each **completed** order. Cancelled and fully refunded orders pay none, so the platform only makes money when the buyer is happy.

<Comparison
  columns={['Per order', 'How it is calculated']}
  rows={[
    ['Seller base', 'Item total after product discount − shop voucher'],
    ['Commission', 'Commission rate × seller base (rate per category, frozen at payment)'],
    ['Seller payout', 'Seller base − commission'],
    ['Buyer pays', 'Seller base − platform voucher share + shipping fee'],
    ['Platform revenue', 'Commission − platform voucher share'],
  ]}
/>

Platform vouchers are paid for by the platform, never by the seller, and shipping is passed straight through to the carrier. The default commission rate is still an open question; the mock-ups use 5% as a placeholder.

## 7. Order flow.

Every order follows one path, and every step answers three questions: **who moves it, where the money is, and what happens if it goes wrong.** A checkout with items from three shops becomes three orders that move on their own.

<Flow
  steps={[
    { status: 'Pending payment', who: 'Buyer · gateway', what: 'The buyer checks out a cart from one or more shops and pays by card with 3-D Secure. Only the gateway’s server callback counts as paid, never the app’s return screen.', money: 'Nothing captured', moneyTone: 'none', branch: { when: 'Not paid within 15 minutes', then: 'Cancelled automatically; vouchers go back to the buyer' } },
    { status: 'To ship', who: 'System', what: 'The checkout splits into one order per shop. Stock is deducted now, at payment, not when an item goes into the cart. Each seller is notified.', money: 'Held in escrow', branch: { when: 'Buyer cancels, or the seller misses the 2-business-day ship deadline', then: 'Cancelled with a full refund; a missed deadline counts against the shop' } },
    { status: 'Ready for pickup', who: 'Seller', what: 'The seller books the carrier pickup and prints the label.', money: 'Held in escrow', branch: { when: 'The seller can’t fulfil it', then: 'Cancels with a reason; full refund, counted against the shop' } },
    { status: 'Shipping', who: 'Carrier', what: 'The status follows the carrier’s webhook; if it goes quiet for 24 hours, the system polls tracking.     { status: 'Paid out', who: 'Finance', what: 'Each week Finance reviews the payout batch, holds sellers if needed, and approves the bank transfer.', money: 'Paid to the seller’s bank', moneyTone: 'released', final: true },
  ]}
  caption="Every time limit here is a setting the admin team can change, not a hard-coded rule."
/>

**The decisions behind it:**

- **One order per shop.** Shops ship, cancel and refund separately, so one late seller never blocks the rest of the buyer’s checkout.
- **Escrow until Completed.** The seller only gets paid once the buyer has the item, or has had 7 days to complain. That single rule is what lets a buyer trust a shop they have never heard of.
- **No cancelling once it ships.** After pickup, the only path is a return. Two ways to undo the same order would mean two sets of rules, and more disputes.

## 8. Return flow.

Returns are where marketplaces lose trust, so the flow gives every side a deadline and makes silence count.

    { status: 'Awaiting the parcel', who: 'Buyer · carrier', what: 'The buyer sends the item back through the integrated carrier. The seller pays return shipping when the seller is at fault.', money: 'Held in escrow' },

  caption="While a return is open, the order’s money stays in escrow and cannot be paid out."

**The decisions behind it:**

- **Silence is a yes.** A seller who ignores a request cannot stall the buyer; the deadline decides for them.
- **The platform decides disputes, not the seller.** Customer support sees both sides’ evidence on one screen, and their decision is final.
- **No change of mind in the MVP.** Every accepted reason is a real problem with the order (not received, wrong, damaged, not as described, missing parts), which keeps the first version of the rules simple enough to run.

## 11. What's next.

The build follows the money, so each phase ends with something testable end to end:

1. **Foundation:** accounts, admin roles and audit log, categories, settings, gateway and carrier sandboxes.
2. **Sell side:** shops and products in Seller Center, moderation in the Admin Portal.
3. **Buy side:** browse, search, cart, checkout, card payment, order split.
4. **Fulfilment and money:** shipping, order statuses, ledger, escrow, commission, payouts, reconciliation.
5. **After-sales and promotion:** cancellations, returns, disputes, refunds; vouchers; reviews; notifications.
6. **Pilot**, then **public launch**.

Before that, a short list of open questions has to be answered: the launch market, the payment gateway and carrier, the default commission rate, and who pays return shipping when a claim is rejected.
